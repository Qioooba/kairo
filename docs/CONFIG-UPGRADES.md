# 配置与用户数据升级规范

## 不变量

1. 正常安装和升级只替换 EXE，不携带 `config.yaml`，也不覆盖用户数据。
2. Windows 默认配置位于 `%AppData%\Kairo\config.yaml`；相对目录均以该目录为基准。
3. 服务器配置、宠物、便笺、提醒、任务、偏好、凭据、数据库连接、HTTP/SOAP 用例、下载元数据和许可证都属于用户数据。
4. 任一关键文件不能完成升级时，本次升级不得提交任何文件。
5. 旧程序不得写入由新程序生成的数据。文件版本和产品版本两层检查都必须通过。

## 启动升级流程

1. `config.PrepareForUpgrade` 只在内存中读取配置，用于定位数据目录；已有配置此时不落盘。
2. `upgrade.Run` 获取升级锁，检查产品是否降级，并逐个验证所有已登记文件。
3. 所有迁移先在内存中完成。准备阶段有任何错误，磁盘保持不变。
4. 提交前在 `data/backups/upgrades/upgrade-<时间>/` 创建全量快照，并记录每个备份的 SHA-256。
5. 每个数据文件原子替换，`upgrade-state.json` 最后提交；提交失败自动恢复快照。
6. 提交成功后重新从磁盘加载配置，再初始化各业务模块。

升级锁超过 15 分钟视为进程异常退出留下的陈旧锁，可以自动接管。损坏的内部升级清单会先进入快照，再根据已验证的用户文件重建。

## 文件版本规则

- `config.yaml` 使用 `schema_version`；当前版本为 2。
- JSON 存储使用根节点 `version`（宠物历史格式使用 `v`）。
- 新增字段只要可能被旧版本写回时丢失，就必须提升对应文件版本并提供逐版本迁移器。
- 迁移器只能负责 `N -> N+1`，必须保留未知的用户字段和用户创建的记录。
- 新格式读取器必须兼容已发布的旧格式；旧格式在下一次成功写入时可规范化为带版本外壳的新格式。
- 发现未来文件版本时必须拒绝写入，不能当作损坏文件重建。
- `upgrade.DefaultAssets` 是持久化文件总清单。新增持久化文件时，必须同时登记并更新清单完整性测试。

配置中的系统、服务器和日志目录均有永久 ID。升级应按 ID 定位官方条目，不能依赖可能被用户修改的名称或数组位置。

## 主动覆盖与恢复

恢复官方配置：

```text
Kairo_win10.exe --reset-config
```

该操作先备份旧配置，再替换服务器等配置；`data_dir`、`download_dir`、`log_dir`、凭据存储方式和 file 凭据密钥会保留。因此宠物、便笺、提醒、任务、凭据等数据不删除，也不会因路径改变而“消失”。

恢复升级快照：

```text
Kairo_win10.exe --restore-upgrade "<data目录>\backups\upgrades\upgrade-..."
```

恢复前会再创建一份当前状态安全快照。快照必须位于受管备份目录内，文件名、目标路径和 SHA-256 全部通过校验后才会恢复；恢复完成后程序退出，重新启动时再按当前版本执行升级。

直接运行旧版属于降级。若数据已被更高产品版本打开，旧版会拒绝启动写入；应先恢复与旧版匹配的升级快照。

## 发布检查

每次涉及持久化结构的发布至少覆盖：旧格式读取、逐版本迁移、幂等重跑、未来版本拒写、准备失败零改动、提交失败回滚、快照篡改拒绝、人工恢复、产品降级拒绝、竞态检测、Windows 交叉编译，以及发布 ZIP 不包含 `config.yaml`。
