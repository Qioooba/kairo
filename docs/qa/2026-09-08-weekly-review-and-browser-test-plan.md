## 2. 需要修复的代码问题

### R1 / P1：代码生成接口缺少管理员权限检查

位置：`internal/httpserver/handlers_wscodegen.go:19`，重点是 30–35 行的 generate / download-zip / push-project 分发，及 92、145 行开始的 handler。

触发条件：开启 token 认证，以非 admin 用户调用代码生成功能。公共认证层只确认 token/IP，不自动限制角色；这些 handler 没有 `requireAdmin`。`GenerateContext` 可以向任意指定输出目录写文件；tool 模式、JDK 探测还会执行本地程序。同一项目的比对写回、打包和计划任务写操作已有管理员检查，这里形成新增的权限绕过入口。

后果：普通用户可执行应由管理员控制的本地写入或工具操作。不是“未登录即可执行”的结论，利用条件是通过现有认证。

建议：按操作定义权限，在进入本地探测/文件访问/执行路径前检查。不能只禁用前端按钮。验证普通用户得到 403，且输出目录和进程均无副作用；管理员成功路径单独验证。

### R2 / P1：“新建文件”会清空已有同名文件

位置：`internal/httpserver/handlers_ssh_sftp.go:811`；入口 `web/pages/files.js` 的 `doNewFile`；底层 `internal/sftpclient/sftpclient.go:222`。

触发：目录中已有非空 `keep.txt`，页面点击“新建文件”，再次输入 `keep.txt`。handler 把空 reader 交给 `UploadStream`，真实 SFTP 实现调用 `Create`，shell 兜底也是覆盖写入语义。没有同名冲突检查或排他创建。

后果：原文件内容丢失，前端还会提示创建成功。

建议：提供排他创建接口（底层原子地拒绝已存在目标），前端显示同名冲突。不能只用先 Stat 再 Create，仍有竞争窗口。测试必须比较操作前后实际文件大小和 SHA256。

### R3 / P1：便笺 SSE 推进草稿版本，绕过并发冲突保护

位置：`web/notes.js:247`–257，特别是 `local.revision = data.note.revision`；保存路径 143–149 行。

触发：A、B 两个窗口打开同一条便笺；A 在列表内编辑但未保存；B 保存另一份正文；A 收到 SSE。当前代码保留 A 的旧正文/草稿，却把版本号更新为 B 的最新 revision。A 随后保存，`update` 使用这个最新 revision。

后果：服务端认为版本匹配，A 的旧草稿直接覆盖 B 的修改，本应出现的 409/冲突选择框不会出现。

建议：草稿保留开始编辑时的 base revision，最新服务端快照独立保存；用户明确解决冲突后才能提升提交版本。验证必须使用两个真实浏览器页面，并等待 B 的事件到达 A 后再保存，不能仅制造一次立即返回的 409。

### R4 / P2：目录同步遗漏空目录

位置：`internal/httpserver/handlers_compare_workbench.go:570`–575；`ensureCompareTargetDir` 在目标不存在时只返回 nil，并不创建目录。

触发：源目录含 `empty/` 或 `nested/empty/`，选择目录同步到另一侧。展开目录时所有 `file.IsDir` 条目被跳过，计划只包含文件；后续 MkdirAll 仅为文件创建父目录。

后果：纯空目录不会落到目标；混合目录中的空子目录也丢失。可能显示同步完成但再次比对仍有“仅左/仅右”。

建议：同步计划显式包含目录创建，并区分目录/文件计数、冲突与失败。增加纯空目录、嵌套空目录、目录与文件同名冲突的验收。

### R5 / P2：代码生成遇到后续同名文件时留下部分产物

位置：`internal/wscodegen/generate.go:327`–353，`writeFiles`。

触发：关闭覆盖，生成文件列表中的第一个文件不存在、后面的某个文件已存在。循环先写前面的文件，碰到冲突才返回错误；HTTP handler 只返回失败，没有回滚和明确的部分写入清单。

后果：“生成失败”后工程已经发生部分修改，重试又会被刚生成的文件阻挡。写入中途磁盘失败也存在类似问题。

建议：写前全量检查目标并采用 staging/发布回滚策略；若产品选择允许部分成功，必须明确返回已写文件和恢复方式。验收检查完整目录快照，不能只断言错误提示出现。

### R6 / P2：偏好文件读取失败被当作空偏好

位置：`internal/preferences/store.go:130`–137。

触发：`os.ReadFile` 因权限、共享锁或 I/O 错误返回空数据和非 NotExist 错误。代码先判断 `len(raw) == 0`，在检查 err 前返回空文档。

后果：页面把读取失败误报成没有保存过偏好；如果目录可写且后续替换成功，Put/ReplaceGlobal 可能以空文档为基底覆盖其他命名空间或用户的偏好。

建议：先分别处理 NotExist 和其他读取错误，仅在读取成功时把零长度文件解释为空。故障测试应断言报错、已有文件哈希不变，不得恢复为默认值后静默保存。

### R7 / P2：指定的 JDK 无效时静默改用自动探测结果

位置：`internal/wscodegen/tool.go:37`–44；探测源见 `internal/wscodegen/detect.go`。

触发：用户填写失效的工程 JDK Home，本机仍有 JAVA_HOME/PATH/其他安装目录的 JDK。`InspectJDKHome` 失败后直接采用 `DetectJDKs("")[0]`。

后果：界面所选 JDK 与实际执行环境不一致，可能用过新的 JDK 生成，或报“没有 wsimport”而不是“指定 JDK 不可用”。这与页面明确标注的工程 JDK 兼容策略不一致。

建议：显式填写但无效应报错；自动探测只作为可选列表，实际采用前应明确显示。用 JDK 6/8 与现代 JDK 并存环境验证实际命令和产物。

## 7. 已有测试与本方案的差距

- `tests/e2e/click-compare-fixtures.js` 有真实点击和夹具基础，但启动的是独立 headless Edge，不是内置浏览器；不能直接作为本轮 iab 实测结果。
- `tests/e2e/tests/37-wscodegen-deep.js`、`38-notes-deep.js` 混合 UI 和页面内 fetch 来准备/修改业务数据。可以借鉴夹具和断言，但需把本次验收的核心业务动作改为实际点击；双窗口竞争要真实发生。
- `39-ui-workbench.js` 包含布局测量，但一些缺失控件分支返回 null 后没有失败。下一轮必须把“必需元素不存在”计为失败，不能跳过断言。
- 仓库未提交的 `run-real-*` 等脚本不属于本次被审版本，也未执行。历史截图/报告不能作为这 19 个提交当前正确性的证明。

## 8. 执行顺序与完成标准

1. 环境与权限基线、夹具及证据目录准备。
2. R1–R7 定向真实复现；损坏路径只使用可恢复夹具，留下失败证据。
3. 比对 → 打包 → 历史比较；WebService → 代码生成 → ZIP/工程 → 编译/SOAP 两条主链。
4. 文件/日志/SSH；便笺/提醒/任务；配置/公共页面。
5. 受控故障、双窗口并发、大数据、重启/升级恢复与原生补测。
6. 下一轮修复后只先重跑对应失败项和关联链，再做最后冒烟，防止修复一个点破坏另一个页面。

每例状态为 PASS / FAIL / BLOCKED / NOT RUN。通过率分母包含已承诺用例，BLOCKED 不算通过。缺失的 JDK/远端服务/原生能力逐项保留，不用 mock 消除阻塞。P1 问题未关闭前不建议把涉及功能视为可发布；本轮只交付审核与方案，不实施修复或测试。
